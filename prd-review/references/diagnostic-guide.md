# 低分诊断指南

> **用途：** 当某个维度得分异常低时，快速定位根因并给出改进建议。
>
> **触发条件：**
> - 单个维度得分率 < 40%（严重缺陷）时必查
> - 单个维度得分为 0 时必查
> - 整体得分不及格（< 60）时查阅 Common Issues
>
> **使用方式：** 在评审报告的"改进路径"章节中，参考此指南给出针对性的补充建议。

---

## 各维度得分低的原因

### 完整性得分极低（< 40%）

**根因：**
- PRD 只有功能列表，缺少背景和用户故事 → 技术无法理解"为什么做"
- 只写了正常流程，异常分支用"应正确处理异常"一笔带过 → 技术实现时全是边界条件
- 业务数据需求缺失 → 接口字段全靠技术自己猜

**解决：** 补充背景、用户故事、异常分支、数据模型字段定义

---

### 清晰度得分极低（< 40%）

**根因：**
- 同一概念前后叫三个名字 → 技术误解成三个东西
- 引入了项目特有的新概念（如自研功能名称"导播台"、自定义缩写）但没有定义 → 非领域背景的读者无法理解
- "尽可能快" — 不知道是 100ms 还是 3s
- 复杂交互纯文字描述 → 不同人脑补出不同流程
- 没有优先级 → 技术排期无法取舍
- 关键数值只有数字没有边界 — 超时写了 30s，但不知道 30s 是上限还是典型值、超过后系统是重试还是降级还是报错

**注意：** 通用行业术语（如推流/GOP/CDN/RTMP）不在此列——目标团队理应知道，不扣分。仅项目特有概念缺少定义才扣分。

**解决：** 统一术语表、量化所有指标、首次出现的专有名词给出定义、绘制流程图、标注 Must/Should/Could、关键数值补充安全区间和边界行为

---

### 可行性得分为 0 或极低（< 40%）

**根因：**
- 需求描述得像从零开始做，完全不提现有系统 → 技术无法评估改动范围
- 依赖外部团队/服务却未提及 → 延期第一原因
- PM 知道这个需求团队没做过类似东西却不标注 → 技术低估工作量
- 完全未提现有系统关系和外部依赖

**解决：** 补充系统关系说明（复用/改造/新增）、依赖清单、工期量级评估、技术难点标注

---

### 风险识别得分为 0 或极低（< 40%）

**根因：**
- PRD 涉及身份证号/生物特征等敏感个人信息却完全不提隐私 → 安全合规直接否决，代码写完了也上线不了
- PRD 涉及姓名/手机号等一般个人信息未标注 → 技术评审时才发现需要脱敏/加密
- 依赖第三方支付服务却不评估 SLA → 上线后挂了不知道找谁
- 没有回滚思路 → 出问题影响面无法评估
- 接入了风控/反垃圾但未定义误伤预案 → 误拦正常用户后只能紧急全关风控，黑名单用户需手动处理
- 隐私/合规/依赖风险无一涉及

**隐私标注分级：**
- **敏感个人信息**（身份证号/生物特征/金融账户/未成年人/健康数据）：准入门槛硬阻塞。PM 只需标注一句"涉及敏感数据需通过隐私合规评审"即可通过
- **一般个人信息**（姓名/手机号/邮箱）：不进准入门槛阻塞，在风险识别维度扣 -3

**解决：** 逐项标注涉及的隐私数据、合规要求、依赖方 SLA、回滚/降级方案；如有风控接入，必须定义误拦恢复流程（解封 SLA、黑白名单管理、策略降级方案）

---

### 可测试性得分极低（< 40%）

**根因：**
- "用户体验好"不是验收标准 → 开发说做完了 PM 说不行，无法判断
- 没定义异常处理预期 → 技术用默认弹窗，PM 说不符合预期
- 没定义成功指标 → 上线后不知道功能到底成没成功
- 验收标准全是形容词
- 关键异常路径（涉及资金/权限/数据写入）只有错误提示，没有恢复验证 → 测试只验证了"报错"没验证"恢复后数据对不对"，异常恢复后可能出现数据不一致

**解决：** 将每个验收标准改为可量化指标、补充异常状态验收标准、定义产品成功度量指标、关键异常路径补充恢复验证标准

---

### UX 一致性得分极低（< 40%）

**根因：**
- 新产品交互与现有产品完全不同 → 用户需要学两套操作逻辑
- 只画了有数据的状态，空态/错误态没定义 → 技术自己猜，猜错了返工
- 面向公众的产品没考虑无障碍 → 合规风险

**关于原型图：**
- 原型图是手段不是目的——如果交互逻辑已用文字/表格清晰描述，即使无原型图也不扣 UX 分
- 评审时在报告中标注"[无原型图] 仅基于文字描述评估"，加分标注交互逻辑是否清晰

**边界情况：**
- 无原型图但交互逻辑清晰 → UX 维度正常评分，标注"[无原型图] 交互逻辑已用文字说明"
- 无原型图且交互逻辑模糊 → 在交互模式/UI 状态检查项扣分，根因是"交互逻辑不清晰"而非"缺少原型"
- 仅原型图无文档 → 标注"评估不完整"，仅评估可判断维度
- 运营活动/内部工具 PRD → UI 状态覆盖率要求降低，仅检查关键异常状态

**解决：** 补充空态/错误态/加载态/边界态的文字说明或原型图、评估无障碍需求（仅 C 端产品）

---

### 逻辑一致性得分极低（< 40%）

**根因：**
- "不可重新开启" vs "可重新开启" 同时出现 → 开发不知道按哪个实现
- 多个 pause 触发条件同时满足时谁优先没定义 → 各端自己猜，行为不一致
- "实时审核 → 命中违规 → ？" 处置级别缺失 → 因果链断裂
- "断连 30s 续录" + "内存 ≤300MB" → 两个约束可能数学上打假
- 修改了现有功能的行为但未说明影响范围 → 研发按新逻辑实现但旧流程被破坏，测试只测了新功能没回归旧流程

**解决：** 逐对检查规则冲突、补充规则优先级、闭合事件链路、验证数值约束自洽、变更已有行为时声明影响范围

---

## Common Issues 常见问题速查

| 问题 | 原因 | 解决 |
|------|------|------|
| 完整性得分极低 | PRD 只有功能列表，无背景/用户故事/异常流程 | 补充背景、用户故事、异常分支 |
| 清晰度得分极低 | 术语混乱、模糊描述多、新概念无定义 | 统一术语表，量化所有指标，首次出现的专有名词给出定义 |
| 文档充满"正确的废话" | 通用正面形容词无量化、数字无来源 | 逐句做删除测试和测量方法追问，将废话替换为可证伪声明 |
| 文档出现"正确的假话" | 数字好看但基线/条件/验证方法缺失 | 每个数字补充：测量方法、统计口径、边界条件 |
| 可行性得分为 0 | 完全未提现有系统关系和外部依赖 | 补充系统关系说明和依赖清单 |
| 风险识别得分为 0 | 隐私/合规/依赖风险无一涉及 | 逐项标注涉及的隐私数据和合规要求 |
| 可测试性得分极低 | 验收标准全是形容词 | 将每个验收标准改为可量化指标，关键异常路径补充恢复验证 |
| UX 一致性得分极低 | 交互逻辑不清、异常状态缺失（空态/错误态/边界态） | 补充各 UI 状态的文字说明或原型图；原型是手段不是目的 |
| 逻辑一致性得分极低 | 跨章节规则矛盾、事件链断裂、状态空洞、变更无影响声明 | 四步法：冲突矩阵→场景穷举→约束方程→影响范围声明 |
| 无原型图但交互清晰 | 用户未提供原型图，但交互逻辑已用文字说明 | 正常评分，标注"[无原型图] 交互逻辑已用文字说明" |
| 无原型图且交互模糊 | 用户未提供原型图，且交互逻辑不清晰 | 在交互模式/UI 状态检查项扣分，根因是"交互逻辑不清晰"而非"缺少原型" |
| 仅原型图无文档 | 部分维度无法评估 | 标注"评估不完整"，仅评估可判断维度 |
