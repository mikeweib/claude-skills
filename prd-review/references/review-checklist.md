# PRD 评审检查清单

审查时逐项对照此清单。每项通过打 ✅，发现问题标注扣分和行号。

## 维度 1：完整性（满分 18）

- [ ] 背景与目标：有明确的业务背景和要解决的问题
- [ ] 目标用户/角色：列出所有涉及角色（含管理员、外部系统）
- [ ] 功能范围 + 排除项：功能列表完整，且明确标注"不做"的边界
- [ ] 用户故事 + 验收条件：每个用户故事有可验证的验收条件
- [ ] 业务流程（正常）：正常流程完整且可闭环
- [ ] 业务流程（异常）：至少覆盖 3 条主要异常路径（网络失败/数据为空/权限不足等）
- [ ] 业务数据需求：需要记录什么信息、业务校验规则、谁可以访问
- [ ] 非功能性需求：性能期望、安全等级要求、兼容范围

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 缺少核心章节（背景/功能范围/用户故事） | -5/项 | -10 |
| 异常流程未覆盖 | -3/条 | -9 |
| 业务数据需求缺失（字段清单/校验规则/权限矩阵） | -4/项 | -8 |
| 非功能性需求缺失（性能/兼容/安全等级） | -3/项 | -6 |

## 维度 2：清晰度（满分 18）

- [ ] 术语统一：同一概念全文使用一致名称，无"一个东西三个叫法"
- [ ] 新概念/领域术语有定义：首次出现的专有名词或新引入的功能名称有解释。注意区分：**通用行业术语**（目标团队理应知道，如音视频领域的推流/GOP/CDN，不扣分）vs **项目特有概念**（本次新引入的功能名/自定义缩写，扣分）。如"导播台"——若为项目新引入的功能名称，对非领域背景的读者（新工程师、跨团队协作者、管理者）必须给出一句话定义
- [ ] 无歧义表述：无不明确的量词和模糊描述（"尽可能快"、"大概 100 条"）
- [ ] 复杂流程有图：3 步以上交互有流程图或时序图
- [ ] 功能优先级标注：Must/Should/Could 分级
- [ ] 关键规则有具体值或示例："订单金额>=200 免运费"而非"满足条件免运费"

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 术语不统一（同一概念多个名称） | -3/处 | -6 |
| 新概念/领域术语缺少定义（仅限项目特有概念，通用行业术语不扣分） | -2/处 | -6 |
| 关键描述有歧义（可读出两种含义） | -4/处 | -8 |
| 复杂流程无图示 | -3/处 | -6 |
| 功能优先级未标注 | -4/次 | -4 |
| 规则缺少具体值或示例 | -2/处 | -6 |

## 维度 3：可行性（满分 13）

- [ ] 与现有系统的关系说明：哪些复用、哪些改造、哪些新增
- [ ] 外部依赖声明：第三方服务、其他团队交付物、平台能力
- [ ] 已识别技术难点标注：PM 视角下的不寻常技术挑战
- [ ] 工期评估有依据：对标参考或经验判断，不需要精确到人天

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 未说明与现有系统的关系（复用/改造/新增） | -5/次 | -5 |
| 外部依赖未声明 | -4/项 | -8 |
| 已有明确技术难点却未标注 | -3/处 | -6 |
| 工期评估无任何依据 | -3/次 | -3 |

## 维度 4：风险识别（满分 13）

- [ ] 业务风险识别：用户不接受、操作门槛高、数据准确性问题
- [ ] 用户隐私数据标注：是否涉及 PII，是否标注
- [ ] 依赖风险评估：依赖方 SLA、是否有备选方案
- [ ] 回滚/降级思路：上线出问题影响多大、能否快速回退
- [ ] 风控/安全拦截的误伤预案：当 PRD 涉及风控/反垃圾/安全拦截/人机验证时，需检查是否定义了：① 误拦恢复流程（用户被误拦后如何解封、SLA 是多少）；② 黑白名单管理机制（谁可以操作、如何批量处理）；③ 风控策略的降级/灰度方案（紧急情况下能否按维度关闭而非全停）
- [ ] 合规要求：金融/医疗/未成年人等特殊领域合规

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 涉及用户隐私数据却未标注 | -5/次 | -5 |
| 依赖风险未评估（外部服务/其他团队） | -4/项 | -8 |
| 无回滚/降级思路 | -3/次 | -3 |
| 风控/安全拦截有接入但无误伤预案（误拦恢复/黑白名单/策略降级） | -4/次 | -4 |
| 合规要求未提及 | -5/次 | -5 |

## 维度 5：可测试性（满分 13）

- [ ] 验收标准可量化：数字、百分比、时间范围，而非形容词
- [ ] 核心路径验收场景：每个核心路径有可验证的使用场景
- [ ] 异常状态验收标准：错误提示文案、重试行为、超时处理预期
- [ ] 成功度量指标：上线后看什么指标判断功能成功

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 验收标准不可量化 | -4/处 | -8 |
| 异常状态验收标准缺失 | -3/处 | -6 |
| 缺少成功度量指标 | -3/次 | -3 |

## 维度 6：UX 一致性（满分 13）

- [ ] 交互模式与现有产品一致：不引入冲突的操作逻辑
- [ ] UI 状态覆盖完整：加载态/空态/错误态/边界态
- [ ] 关键页面有原型/线框图
- [ ] 无障碍/国际化需求标注（如需要）

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 交互模式与现有产品冲突 | -4/处 | -8 |
| UI 状态覆盖不全（空态/错误态/边界态缺失） | -3/处 | -6 |
| 关键页面无原型/线框图 | -3/页面 | -6 |
| 需要无障碍却未提及 | -3/次 | -3 |

## 维度 7：逻辑一致性（满分 12）

> 跨章节交叉验证——规则之间是否自洽。

- [ ] 规则无直接矛盾：相同条件不会推出互斥结论
- [ ] 规则竞争有优先级：多规则覆盖同一场景时，有明确的裁决顺序
- [ ] 因果链闭合：每个触发事件 → 中间动作 → 最终结果，链路完整
- [ ] 数值约束自洽：时间/容量/频率约束可同时满足
- [ ] 状态机完备：每种状态 × 每种事件都有定义的行为（含显式"无操作"）—— **涉及客户端功能时，对照 `system-event-inventory.md` 逐平台检查系统级中断事件**
- [ ] 角色权限一致：同一角色在不同章节的权限描述无矛盾

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 直接矛盾（两个声明互斥） | -5/处 | -10 |
| 规则竞争无优先级（同场景多规则结论不同） | -4/处 | -8 |
| 因果链断裂（事件链缺少关键跳） | -3/处 | -6 |
| 数值约束冲突（约束不可同时满足） | -3/处 | -6 |
| 状态/事件无定义（状态机空洞） | -2/处 | -6 |
| 角色权限不一致（同角色不同章节权限矛盾） | -3/处 | -6 |

## 信号质量扫描（逐维度交叉验证）

每个维度审查结束时执行。信号质量不独立打分，作为各维度的**降级因子**。

### 两类问题

**正确的废话：** 删掉不影响信息量。**检测：删除测试 + 可证伪测试。**

**正确的假话：** 有数字但无法复现。**检测：测量方法追问 + 基线追问 + 边界追问。**

### 五条检测规则

| # | 规则 | 检测动作 | 触发词 |
|---|------|---------|--------|
| 1 | **删除测试** | 删掉这句话，信息量是否减少？ | 通用正面形容词组合 |
| 2 | **可证伪测试** | 如果声明是错的，能用什么证据证明？ | "提升"、"优化"、"改善"、"保证" |
| 3 | **测量方法追问** | 数字怎么得出的？谁在什么条件下测量？ | 百分比、具体数字、时间指标 |
| 4 | **基线追问** | 对比的是什么？基线数据从哪来？ | "提升 X%"、"降低 X%" |
| 5 | **边界追问** | 什么条件下这个声明不成立？ | "所有"、"完全"、"自动"、"无需" |

### 降级规则

| 废话/假话密度 | 后果 |
|-------------|------|
| 某维度 > 30% 关键声明是废话/假话 | 该维度得分**封顶 60%** |
| 某维度 > 50% 关键声明是废话/假话 | 该维度直接**降至 0 分** |

"关键声明"界定：目标/指标、功能核心动作、验收标准、性能数字、约束规则。
