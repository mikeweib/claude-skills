# 需求评审

## Overview

对产品需求文档（PRD）进行 6 维度综合评审，给出 0-100 分量化评分和 A-F 等级。输入支持 Markdown PRD 文件 + 原型图/截图混合输入。

**目标用户：** 技术负责人/架构师（技术评审前过 PRD 质量关），产品经理（提交 PRD 前自检）。

## When to Use 触发条件

- 用户要求"需求评审"、"PRD 打分"、"评审需求文档"、"检查 PRD 质量"
- 技术评审前评估 PRD 是否达到准入门槛
- PM 提交 PRD 前自查
- 用户直接提供 PRD 文件或原型图要求评审

**不使用的情况：**
- 技术方案评审（属于技术设计文档评审，非 PRD 评审）
- 代码审查（使用语言专用 review skills）
- UI 设计评审（仅涉及视觉美感，非产品需求层面）
- 安全漏洞扫描（使用 `security-review` skill）

## Scoring Workflow 评分流程

> **评分体系：** 6 个维度，满分 100。及格线 60 分（C 级）。

| 维度 | 权重 | 核心问题 |
|------|------|---------|
| 完整性 | 20% | 该有的内容都有吗？异常流程、业务数据需求覆盖了吗？ |
| 清晰度 | 20% | 写出来的东西无歧义、术语统一、能直接执行吗？ |
| 可行性 | 15% | 考虑现实约束了吗？外部依赖明确吗？ |
| 风险识别 | 15% | 业务雷区标注了吗？隐私/合规/依赖风险评估了吗？ |
| 可测试性 | 15% | 验收标准可量化吗？异常状态有验收标准吗？ |
| UX 一致性 | 15% | 交互与现有产品一致吗？UI 状态覆盖完整吗？ |

### Step 1: 输入接收与预处理

确认审查对象：

1. **读取 PRD 文件**：如果用户提供了 Markdown 文件路径，直接读取，识别章节结构
2. **查看原型图**：如果用户提供了原型图/截图路径，查看图片内容，提取 UI 状态、交互路径信息
3. **混合输入**：PRD 文本为主，原型图为补充验证
4. **纯对话输入**：如果用户直接在对话中贴出需求内容，以对话内容作为审查对象

**输出：** 识别的输入类型 / PRD 大致结构 / 章节覆盖情况

> **边界情况：** 仅提供原型图无 PRD 文本时，完整性/清晰度/可行性维度只能基于视觉内容做有限评估，需在报告中标注"因缺少 PRD 文档，以下维度无法完整评审"。此时总分仅基于可评估维度，并标注"评估不完整"。

### Step 2: 逐维度审查

按顺序逐一审查 6 个维度。每个维度的审查方法：

1. 列出该维度检查清单（见下方各维度详情或 `references/review-checklist.md`）
2. 逐条对照 PRD 内容，记录证据
3. 发现缺失/缺陷时，给出 `[事实]` 标注（引用原文行号或截图位置）和扣分
4. 无法从 PRD 中确认的内容，标注为 `[推测]`，不扣分但记录在报告中

**扣分约束：**
- 每个维度的扣分不超过其满分
- 同一问题不跨维度重复扣分
（当问题同时涉及多个维度时，在关联度最高的维度扣分，并在其他维度的报告中注明"已在 XX 维度扣分"）

---

#### 维度 1：完整性（满分 20）

> PM 的核心职责——该有的内容是否都有。

**检查项：**

- [ ] 背景与目标：有明确的业务背景和要解决的问题
- [ ] 目标用户/角色：列出所有涉及角色（含管理员、外部系统）
- [ ] 功能范围 + 排除项：功能列表完整，且明确标注"不做"的边界
- [ ] 用户故事 + 验收条件：每个用户故事有可验证的验收条件
- [ ] 业务流程（正常流程）：完整且可闭环
- [ ] 业务流程（异常）：至少覆盖 3 条主要异常路径
- [ ] 业务数据需求：需要记录什么信息、业务校验规则、谁可以访问
- [ ] 非功能性需求：性能期望、安全等级要求、兼容范围

| 缺失 | 扣分 | 上限 |
|------|------|------|
| 缺少核心章节（背景/功能范围/用户故事） | -5/项 | -10 |
| 异常流程未覆盖（至少 3 条主要异常路径） | -3/条 | -9 |
| 业务数据需求缺失（字段清单/校验规则/权限矩阵） | -4/项 | -8 |
| 非功能性需求缺失（性能/兼容/安全等级） | -3/项 | -6 |

**PM 必须给出（区别于技术评审）：**
- 背景与目标、目标用户、功能范围与排除项、用户故事与验收条件
- 业务流程：正常 + 至少主要异常分支
- 业务数据需求：需要记录的信息、业务校验规则、访问权限
- 非功能性需求：用户感知的性能期望、安全等级要求、兼容范围

**PM 不必给出：** 数据库表结构/索引/存储方案、API 接口定义、技术实现细节

**得分低的原因：**
- PRD 只有功能列表，缺少背景和用户故事 → 技术无法理解"为什么做"
- 只写了正常流程，异常分支用"应正确处理异常"一笔带过 → 技术实现时全是边界条件
- 业务数据需求缺失 → 接口字段全靠技术自己猜

---

#### 维度 2：清晰度（满分 20）

> PM 的表达能力——写出来的东西是否无歧义、能直接执行。

**检查项：**

- [ ] 术语统一：同一概念全文使用一致名称
- [ ] 新概念/领域术语有定义：首次出现的专有名词或新引入的功能名称有解释
- [ ] 无歧义表述：无"尽可能快"、"大概"、"适当"等模糊词
- [ ] 复杂流程有图：3 步以上交互有流程图或时序图
- [ ] 功能优先级标注：Must/Should/Could 分级
- [ ] 关键规则有具体值或示例

| 问题 | 扣分 | 上限 |
|------|------|------|
| 术语不统一（同一概念多个名称） | -3/处 | -6 |
| 新概念/领域术语缺少定义（首次出现未解释） | -2/处 | -6 |
| 关键描述有歧义（可读出两种含义） | -4/处 | -8 |
| 复杂流程无图示（3 步以上交互） | -3/处 | -6 |
| 功能优先级未标注 | -4/次 | -4 |
| 规则缺少具体值或示例 | -2/处 | -6 |

**PM 必须给出：** 统一的术语表、新概念/领域术语的定义、无歧义的具体描述、复杂流程的图示、功能优先级、关键规则的量化值

**PM 不必给出：** 技术实现细节、API 字段定义

**得分低的原因：**
- 同一概念前后叫三个名字 → 技术误解成三个东西
- 引入了领域专有名词（如"导播台"、"GOP"、"RTMP"）但没有定义 → 非领域背景的读者无法理解
- "尽可能快" → 不知道是 100ms 还是 3s
- 复杂交互纯文字描述 → 不同人脑补出不同流程
- 没有优先级 → 技术排期无法取舍

---

#### 维度 3：可行性（满分 15）

> PM 的工程意识——是否考虑了现实约束。

**检查项：**

- [ ] 与现有系统的关系说明：哪些复用、哪些改造、哪些新增
- [ ] 外部依赖声明：第三方服务、其他团队交付物、平台能力
- [ ] 已识别技术难点标注：PM 视角下团队以前没做过的技术挑战
- [ ] 工期评估有依据：对标参考或经验判断

| 缺失 | 扣分 | 上限 |
|------|------|------|
| 未说明与现有系统的关系（复用/改造/新增） | -5/次 | -5 |
| 外部依赖未声明（第三方服务/其他团队交付物） | -4/项 | -8 |
| 已有明确技术难点却未标注 | -3/处 | -6 |
| 工期评估无任何依据 | -3/次 | -3 |

**PM 必须给出：** 与现有系统的关系、外部依赖声明、已识别的技术难点、工期量级评估（天/周/月）

**PM 不必给出：** 技术方案选型/架构设计、性能基准测试预估、代码层面可行性分析

**得分低的原因：**
- 需求描述得像从零开始做，完全不提现有系统 → 技术无法评估改动范围
- 依赖外部团队/服务却未提及 → 延期第一原因
- PM 知道这个需求团队没做过类似东西却不标注 → 技术低估工作量

---

#### 维度 4：风险识别（满分 15）

> PM 的风险嗅觉——业务的雷区是否标注。

**检查项：**

- [ ] 业务风险识别：用户不接受、操作门槛高、数据准确性问题
- [ ] 用户隐私数据标注：是否涉及 PII，是否标注
- [ ] 依赖风险评估：依赖方 SLA、是否有备选方案
- [ ] 回滚/降级思路：上线出问题影响多大、能否快速回退
- [ ] 合规要求：金融/医疗/未成年人等特殊领域合规

| 缺失 | 扣分 | 上限 |
|------|------|------|
| 涉及用户隐私数据却未标注 | -5/次 | -5 |
| 依赖风险未评估（外部服务/其他团队） | -4/项 | -8 |
| 无回滚/降级思路 | -3/次 | -3 |
| 合规要求未提及（金融/医疗/未成年人等） | -5/次 | -5 |

**PM 必须给出：** 业务风险评估、隐私数据标注、依赖风险、回滚/降级思考、合规要求

**PM 不必给出：** 安全漏洞分析、技术架构风险（技术评审的事）

**得分低的原因：**
- PRD 涉及用户手机号/身份证却完全不提隐私 → 技术评审时才发现需要脱敏/加密
- 依赖第三方支付服务却不评估 SLA → 上线后挂了不知道找谁
- 没有回滚思路 → 出问题影响面无法评估

---

#### 维度 5：可测试性（满分 15）

> PM 的验收能力——需求是否可被验证。

**检查项：**

- [ ] 验收标准可量化：数字、百分比、时间范围，而非形容词
- [ ] 核心路径验收场景：每个核心路径有可验证的使用场景
- [ ] 异常状态验收标准：错误提示文案、重试行为、超时处理预期
- [ ] 成功度量指标：上线后看什么指标判断功能成功

| 问题 | 扣分 | 上限 |
|------|------|------|
| 验收标准不可量化（"用户体验好"、"加载快"） | -4/处 | -8 |
| 异常状态验收标准缺失 | -3/处 | -6 |
| 缺少成功度量指标 | -3/次 | -3 |

**PM 必须给出：** 可量化的验收标准、核心路径验收场景、异常状态验收标准、数据指标/成功度量

**PM 不必给出：** 测试用例、测试策略、QA 计划

**得分低的原因：**
- "用户体验好"不是验收标准 → 开发说做完了 PM 说不行，无法判断
- 没定义异常处理预期 → 技术用默认弹窗，PM 说不符合预期
- 没定义成功指标 → 上线后不知道功能到底成没成功

---

#### 维度 6：UX 一致性（满分 15）

> PM 的设计感知——交互是否与现有产品一致、UI 状态是否完整。

**检查项：**

- [ ] 交互模式与现有产品一致：不引入冲突的操作逻辑
- [ ] UI 状态覆盖完整：加载态/空态/错误态/边界态
- [ ] 关键页面有原型/线框图
- [ ] 无障碍/国际化需求标注（如需要）

| 问题 | 扣分 | 上限 |
|------|------|------|
| 交互模式与现有产品冲突 | -4/处 | -8 |
| UI 状态覆盖不全（空态/错误态/边界态缺失） | -3/处 | -6 |
| 关键页面无原型/线框图 | -3/页面 | -6 |
| 需要无障碍却未提及 | -3/次 | -3 |

**PM 必须给出：** 关键页面原型/线框图、所有 UI 状态的设计说明、交互模式与现有产品关系的说明

**PM 不必给出：** 像素级视觉稿（设计师的事）、前端组件实现方案

**得分低的原因：**
- 新产品交互与现有产品完全不同 → 用户需要学两套操作逻辑
- 只画了有数据的状态，空态/错误态没定义 → 技术自己猜，猜错了返工
- 关键页面没有线框图 → 技术对页面布局理解不一致
- 面向公众的产品没考虑无障碍 → 合规风险

### 信号质量扫描（逐维度交叉验证）

> 六个维度检查"缺什么"，信号质量扫描检查"说了但没用"和"说了但是假的"。
> 在每个维度审查结束时执行一次，识别该维度中发现的废话和假话。

#### 两类问题

**正确的废话：** 删掉这句话，文档信息量不会有任何改变。特点是使用通用的正面形容词但零具体信息。

| 示例 | 为什么是废话 | 检测方法 |
|------|------------|---------|
| "提升用户体验" | 哪个功能不声称提升体验？ | **删除测试**：删掉这句话，文档信息量是否减少？ |
| "保证系统稳定性" | 几个 9？容忍多久故障？ | **量化追问**：稳定 = 什么指标？阈值多少？ |
| "页面加载要快" | "快"对所有页面都适用 | **量化追问**：多快？什么网络条件？P50 还是 P99？ |
| "支持高并发" | 什么量级？100 QPS 还是 10000？ | **量化追问**：QPS 目标？峰值系数？ |
| "提供流畅的交互体验" | 流畅怎么定义？帧率？响应时间？ | **可证伪测试**：如果交互不流畅，你拿什么数据证明？ |

**正确的假话：** 听起来有数据、很专业，但数字无法复现、测量方法不存在、或者仅在理想条件下成立。

| 示例 | 为什么是假话 | 检测方法 |
|------|------------|---------|
| "配置效率提升 50%" | 对比什么基线？谁测的？怎么测的？ | **基线追问**：基线数据从哪来？实验条件是什么？ |
| "切换成功率 ≥ 99%" | 什么网络条件？统计周期？谁验证？ | **测量方法追问**：这个数字怎么来的？上线后谁来验证？ |
| "支持所有主流浏览器" | 主流包括哪些？内核版本？ | **边界追问**：什么浏览器**明确不支持**？ |
| "自动切换，无需刷新" | 全屏播放时切不切？弱网下切不切？ | **边界追问**：什么条件下这个"自动"会失效？ |
| "兼容现有系统" | 不改代码直接跑？还是需要适配层？ | **覆盖追问**：兼容了哪些系统？实测了吗？ |

#### 五条检测规则

| # | 规则 | 针对 | 检测动作 | 触发词 |
|---|------|------|---------|--------|
| 1 | **删除测试** | 正确的废话 | 删掉这句话，文档信息量是否减少？无减少 → 废话 | 通用正面形容词组合 |
| 2 | **可证伪测试** | 正确的废话 | 如果声明是错的，能用什么证据证明？无证据 → 废话 | "提升"、"优化"、"改善"、"增强"、"保证" |
| 3 | **测量方法追问** | 正确的假话 | 这个数字怎么得出的？谁在什么条件下测量？无答案 → 假话 | 任何百分比、具体数字、时间指标 |
| 4 | **基线追问** | 正确的假话 | 对比的是什么？基线数据从哪来？ | "提升 X%"、"降低 X%"、"缩短 X%" |
| 5 | **边界追问** | 正确的假话 | 在什么条件下这个声明不成立？ | "所有"、"完全"、"自动"、"无需"、"任何"、"全量" |

#### 在评分中的作用

信号质量扫描不独立打分，而是作为**各维度的降级因子**：

- 发现废话/假话时，在对应维度的报告中标注 `[信号]` 并给出追问建议
- 如果某个维度中 > 30% 的关键声明是废话或假话，该维度得分**封顶 60%**（如 15/20 → 实际最高 12/20）
- 如果某个维度中 > 50% 的关键声明是废话或假话，该维度直接**降至 0 分**

**"关键声明"的界定：** 出现在以下位置的陈述视为关键声明——目标/指标、功能描述的核心动作、验收标准、非功能性需求的性能数字、数据模型中的约束规则。

#### 在报告中的呈现

在报告的 "Top 5 问题" 之后增加一个 "信号质量问题" 小节：

```
## 信号质量问题
| 原文 | 问题类型 | 所在维度 | 追问 |
|------|---------|---------|------|
| "降低运营操作门槛" | 正确的废话 — 无量化 | 完整性 | 当前门槛多高？降到什么程度算成功？ |
| "配置效率提升 50%" | 正确的假话 — 无基线 | 可测试性 | 对比什么基线？人工配置单场耗时多少？ |
```

---

### Step 3: 汇总评分

1. 6 个维度得分求和（满分 100，最低 0）
2. 应用信号质量扫描的降级规则（封顶或置零）
3. 不及格项标记：单个维度得分率 < 40% 视为该维度严重缺陷
4. 映射到 A-F 等级

| 得分率 | 等级 | 含义 | 行动 |
|--------|------|------|------|
| >= 90% | **A** | 优秀 — PRD 质量很高 | 可以进入技术评审 |
| >= 75% | **B** | 良好 — 少量待补充项 | 补充后进入技术评审 |
| >= 60% | **C** | 及格 — 关键项基本覆盖 | 补充缺失项后可进入技术评审 |
| >= 30% | **D** | 不及格 — 存在重大遗漏 | 退回补充，重新评审 |
| < 30% | **F** | 严重不足 — 几乎没有可用内容 | 需重新编写 |

**及格线 60 分的含义：** PRD 至少需要：背景/功能范围/用户故事齐全、无严重歧义、外部依赖和现有系统关系明确、隐私/合规风险标注、验收标准可量化、关键页面有原型。

## 核心检查清单

审查时对照此清单（详见 `references/review-checklist.md`）：

- [ ] **完整性** — 背景/功能范围/用户故事/异常流程/业务数据/非功能性需求 到位
- [ ] **清晰度** — 术语统一、新概念有定义、无歧义、复杂流程有图、有优先级、规则有示例
- [ ] **可行性** — 现有系统关系明确、外部依赖声明、技术难点标注、工期有依据
- [ ] **风险识别** — 隐私数据标注、依赖风险评估、回滚思路、合规要求
- [ ] **可测试性** — 验收标准可量化、异常状态验收标准、成功度量指标
- [ ] **UX 一致性** — 交互不冲突、UI 状态完整、有关键原型、无障碍标注
- [ ] **信号质量** — 无正确的废话（可执行删除测试）、无正确的假话（数字有测量方法和基线）

## Quick Reference 速查

| 维度 | 满分 | 最致命的扣分项 | 单次最高扣分 |
|------|------|---------------|-------------|
| 完整性 | 20 | 缺少核心章节 | -5/项 |
| 清晰度 | 20 | 关键描述有歧义 | -4/处 |
| 可行性 | 15 | 未说明与现有系统关系 | -5/次 |
| 风险识别 | 15 | 隐私数据未标注 / 合规未提及 | -5/次 |
| 可测试性 | 15 | 验收标准不可量化 | -4/处 |
| UX 一致性 | 15 | 交互模式冲突 | -4/处 |

## Common Issues 常见问题

| 问题 | 原因 | 解决 |
|------|------|------|
| 完整性得分极低 | PRD 只有功能列表，无背景/用户故事/异常流程 | 补充背景、用户故事、异常分支 |
| 清晰度得分极低 | 术语混乱、模糊描述多、新概念无定义 | 统一术语表，量化所有指标，首次出现的专有名词给出定义 |
| 文档充满"正确的废话" | 通用正面形容词无量化、数字无来源 | 逐句做删除测试和测量方法追问，将废话替换为可证伪声明 |
| 文档出现"正确的假话" | 数字好看但基线/条件/验证方法缺失 | 每个数字补充：测量方法、统计口径、边界条件 |
| 可行性得分为 0 | 完全未提现有系统关系和外部依赖 | 补充系统关系说明和依赖清单 |
| 风险识别得分为 0 | 隐私/合规/依赖风险无一涉及 | 逐项标注涉及的隐私数据和合规要求 |
| 可测试性得分极低 | 验收标准全是形容词 | 将每个验收标准改为可量化指标 |
| UX 一致性得分极低 | 仅有正常状态原型，缺少异常状态 | 补充空态/错误态/加载态/边界态设计 |
| 无原型图时 UX 维度无法评分 | 用户未提供原型图 | 标注"[推测] 无原型图，UX 维度仅基于文字描述评估" |
| 仅原型图无文档 | 部分维度无法评估 | 标注"评估不完整"，仅评估可判断维度 |
