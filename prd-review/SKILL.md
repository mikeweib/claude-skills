# 需求评审

## Overview

对产品需求文档（PRD）进行 7 维度综合评审，给出 0-100 分量化评分和 A-F 等级。输入支持 Markdown PRD 文件 + 原型图/截图混合输入。

**目标用户：** 技术负责人/架构师（技术评审前过 PRD 质量关），产品经理（提交 PRD 前自检）。

## When to Use 触发条件

- 用户要求"需求评审"、"PRD 打分"、"评审需求文档"、"检查 PRD 质量"
- 技术评审前评估 PRD 是否达到准入门槛
- PM 提交 PRD 前自查
- 用户直接提供 PRD 文件或原型图要求评审

**不使用的情况：**
- 技术方案评审（属于技术设计文档评审，非 PRD 评审）
- 代码审查（使用语言专用 review skills）
- UI 设计评审（仅涉及视觉美感，非产品需求层面）
- 安全漏洞扫描（使用 `security-review` skill）

## Scoring Workflow 评分流程

> **评分体系：** 7 个维度，满分 100。及格线 60 分（C 级）。

| 维度 | 权重 | 核心问题 |
|------|------|---------|
| 完整性 | 18% | 该有的内容都有吗？异常流程、业务数据需求覆盖了吗？ |
| 清晰度 | 18% | 写出来的东西无歧义、术语统一、能直接执行吗？ |
| 可行性 | 13% | 考虑现实约束了吗？外部依赖明确吗？ |
| 风险识别 | 13% | 业务雷区标注了吗？隐私/合规/依赖风险评估了吗？ |
| 可测试性 | 13% | 验收标准可量化吗？异常状态有验收标准吗？ |
| UX 一致性 | 13% | 交互与现有产品一致吗？UI 状态覆盖完整吗？ |
| 逻辑一致性 | 12% | 规则之间自洽吗？跨章节有矛盾吗？事件链闭合吗？ |

### Step 1: 输入接收与预处理

确认审查对象：

1. **读取 PRD 文件**：如果用户提供了 Markdown 文件路径，直接读取，识别章节结构
2. **查看原型图**：如果用户提供了原型图/截图路径，查看图片内容，提取 UI 状态、交互路径信息
3. **混合输入**：PRD 文本为主，原型图为补充验证
4. **纯对话输入**：如果用户直接在对话中贴出需求内容，以对话内容作为审查对象

**输出：** 识别的输入类型 / PRD 大致结构 / 章节覆盖情况

> **边界情况处理：**
>
> 每种边界场景有明确的处理动作、评分规则和报告模板，减少自由裁量空间。
>
> | 场景 | 处理方式 | 评分调整 | 报告标注模板 |
> |------|---------|---------|------------|
> | 仅原型图无 PRD 文本 | 完整性/清晰度/可行性仅基于视觉内容有限评估 | 可评估维度正常计分，不可评估维度标注 N/A，总分 = 可评估维度得分 ÷ 可评估维度满分 × 100 | `⚠️ 评估不完整：因缺少 PRD 文档，完整性/清晰度/可行性维度无法完整评审` |
> | PRD 为 PDF/Word/纯文本 | 尝试直接读取；无法解析则提示用户粘贴文本或导出 Markdown | 正常评分（如成功读取）；失败则暂停不评分 | `ℹ️ 输入格式：[PDF/Word/纯文本]，已转换为可评审内容` |
> | PRD 内容极短（< 100 字） | 完整性维度以最低分（0-3 分）起评 | 所有维度正常打分但改进路径中列出所有缺失的核心章节 | `⚠️ 警告：PRD 内容过短（仅 XX 字），缺少核心章节：背景/功能范围/用户故事/异常流程/验收标准。建议补充后重新评审` |
> | 用户同时提供多个 PRD 文件 | 确认范围后逐一评审 | 每个文件独立评分，不合并 | `ℹ️ 共 N 个文件，以下为 [文件名] 的独立评审报告` |
> | PRD 文件无法读取 | 列出可能原因（路径/权限），等待用户重新提供 | 暂停评审，不生成评分 | `❌ 无法读取文件 [路径]：路径错误 / 权限不足 / 文件不存在。请重新提供` |
> | 对话内容无明确章节 | 以"非正式 PRD"模式评审 | 清晰度维度权重降至 50%（上限 9 分），总分标注"仅供参考" | `⚠️ 非正式 PRD 格式：以下评分基于对话中的需求描述，仅供参考。建议整理为正式 PRD 文档后重新评审` |

### Step 2: 逐维度审查

按顺序逐一审查 7 个维度。

**审查流程全景：**

```
Step 2 逐维度审查（7 维度 × 统一流程）
┌──────────────────────────────────────────────────────┐
│ 每个维度：                                            │
│  1. 对照 review-checklist.md 逐项检查                 │
│  2. 发现缺陷 → [事实] 标注行号 + 扣分                  │
│  3. 不确定 → [推测] 记录，不扣分                       │
│  4. 执行信号质量扫描（对照 signal-quality-guide.md）   │
│  5. 得分率 < 40% → 查 diagnostic-guide.md 定位根因    │
│  6. 客户端功能 → 查 system-event-inventory.md         │
├──────────────────────────────────────────────────────┤
│ 维度 1-2    │ 维度 3-6        │ 维度 7               │
│ 完整性 18   │ 可行性 13       │ 逻辑一致性 12         │
│ 清晰度 18   │ 风险识别 13     │ ← 四步法交叉验证      │
│             │ 可测试性 13     │                       │
│             │ UX 一致性 13    │                       │
└──────────────────────────────────────────────────────┘
```

**每个维度的统一审查步骤：**

1. 列出该维度检查清单（详见 `references/review-checklist.md`）
2. 逐条对照 PRD 内容，记录证据
3. 发现缺失/缺陷时，给出 `[事实]` 标注（引用原文行号或截图位置）和扣分
4. 无法从 PRD 中确认的内容，标注为 `[推测]`，不扣分但记录在报告中

**扣分约束：**
- 每个维度的扣分不超过其满分
- 同一问题不跨维度重复扣分
（当问题同时涉及多个维度时，在关联度最高的维度扣分，并在其他维度的报告中注明"已在 XX 维度扣分"）

**参考文件加载策略：**

| 文件 | 加载时机 | 用途 |
|------|---------|------|
| `review-checklist.md` | **始终** — 每个维度审查时 | 检查清单 + 扣分规则 |
| `signal-quality-guide.md` | **每个维度审查结束时** | 废话/假话检测，不独立打分 |
| `diagnostic-guide.md` | **条件触发** — 维度得分率 < 40% | 低分根因分析 + 改进建议 |
| `system-event-inventory.md` | **条件触发** — PRD 涉及客户端功能 | 系统中断事件状态空洞检查 |

#### 维度 1：完整性（满分 18）

> PM 的核心职责——该有的内容是否都有。
>
> **检查清单与扣分规则：** 详见 `references/review-checklist.md` 维度 1

**PM 必须给出（区别于技术评审）：**
- 背景与目标、目标用户、功能范围与排除项、用户故事与验收条件
- 业务流程：正常 + 至少主要异常分支
- 业务数据需求：需要记录的信息、业务校验规则、访问权限
- 非功能性需求：用户感知的性能期望、安全等级要求、兼容范围

**PM 不必给出：** 数据库表结构/索引/存储方案、API 接口定义、技术实现细节

> **得分异常？** 当本维度得分率 < 40% 时，查阅 `references/diagnostic-guide.md` 完整性章节定位根因。

---

#### 维度 2：清晰度（满分 18）

> PM 的表达能力——写出来的东西是否无歧义、能直接执行。
>
> **检查清单与扣分规则：** 详见 `references/review-checklist.md` 维度 2

**PM 必须给出：** 统一的术语表、新概念/领域术语的定义、无歧义的具体描述、复杂流程的图示、功能优先级、关键规则的量化值

**PM 不必给出：** 技术实现细节、API 字段定义

> **得分异常？** 当本维度得分率 < 40% 时，查阅 `references/diagnostic-guide.md` 清晰度章节定位根因。

---

#### 维度 3：可行性（满分 13）

> PM 的工程意识——是否考虑了现实约束。
>
> **检查清单与扣分规则：** 详见 `references/review-checklist.md` 维度 3

**PM 必须给出：** 与现有系统的关系、外部依赖声明、已识别的技术难点、工期量级评估（天/周/月）

**PM 不必给出：** 技术方案选型/架构设计、性能基准测试预估、代码层面可行性分析

> **得分异常？** 当本维度得分率 < 40% 时，查阅 `references/diagnostic-guide.md` 可行性章节定位根因。

---

#### 维度 4：风险识别（满分 13）

> PM 的风险嗅觉——业务的雷区是否标注。
>
> **检查清单与扣分规则：** 详见 `references/review-checklist.md` 维度 4

**PM 必须给出：** 业务风险评估、隐私数据标注、依赖风险、回滚/降级思考、合规要求

**PM 不必给出：** 安全漏洞分析、技术架构风险（技术评审的事）

> **得分异常？** 当本维度得分率 < 40% 时，查阅 `references/diagnostic-guide.md` 风险识别章节定位根因。

---

#### 维度 5：可测试性（满分 13）

> PM 的验收能力——需求是否可被验证。
>
> **检查清单与扣分规则：** 详见 `references/review-checklist.md` 维度 5

**PM 必须给出：** 可量化的验收标准、核心路径验收场景、异常状态验收标准、数据指标/成功度量

**PM 不必给出：** 测试用例、测试策略、QA 计划

> **得分异常？** 当本维度得分率 < 40% 时，查阅 `references/diagnostic-guide.md` 可测试性章节定位根因。

---

#### 维度 6：UX 一致性（满分 13）

> PM 的设计感知——交互是否与现有产品一致、UI 状态是否完整。
>
> **检查清单与扣分规则：** 详见 `references/review-checklist.md` 维度 6

**PM 必须给出：** 关键页面原型/线框图、所有 UI 状态的设计说明、交互模式与现有产品关系的说明

**PM 不必给出：** 像素级视觉稿（设计师的事）、前端组件实现方案

> **得分异常？** 当本维度得分率 < 40% 时，查阅 `references/diagnostic-guide.md` UX 一致性章节定位根因。

---

#### 维度 7：逻辑一致性（满分 12）

> PRD 的内部自洽——规则之间是否打架、事件链是否闭合、约束是否可同时满足。

**核心理念：** 前 6 个维度检查每个章节"单独看"的质量，逻辑一致性检查"跨章节放在一起看"是否自洽。每条规则单独都合理，不等于放在一起不冲突。

**检查方法：四步法**

**Step A — 规则提取：** 从 PRD 中提取所有"如果 X 则 Y"的规则声明（状态转换条件、业务规则、约束条件），每条标注来源行号。

**Step B — 冲突矩阵：** 两两比对规则，找出：
- **直接矛盾**：相同触发条件 X，结论 Y 互斥（如 A 章说"不可重新开启"，B 章说"可重新开启"）
- **规则竞争**：同一场景下多条规则同时生效但结论不同，且未定义优先级

**Step C — 场景穷举：** 对关键状态机/流程，穷举可能的输入事件，检查：
- **因果链断裂**：事件发生 → 触发动作 → ？ → 最终结果，中间缺失关键一跳
- **无主规则**：同一场景多个规则同时触发，未定义裁决优先级
- **状态空洞**：某种状态 × 某种事件组合下行为未定义

> **平台系统事件检查：** 当 PRD 涉及客户端功能（移动端/桌面端/嵌入式设备）时，对照 `references/system-event-inventory.md` 中对应平台的事件清单，逐条检查 PRD 是否定义了每个系统级中断事件的行为。此清单不逐条扣分——仅当 PRD 未定义的事件属于该需求的**合理风险场景**时才记录为状态空洞。纯后端/纯 Web 后台管理类 PRD 可跳过此检查。

**Step D — 约束方程：** 提取所有数值约束（时间、容量、频率），检查是否存在数学上不可能同时满足的组合。如"断连 30s 内续录" + "内存 ≤300MB" —— 30s 的 720p 缓存数据量是否超出 300MB？

**检查清单与扣分规则：** 详见 `references/review-checklist.md` 维度 7

**PM 必须给出：** 规则之间不矛盾、多规则触发时有优先级裁决、事件链路完整闭合、数值约束可同时成立

**PM 不必给出：** 形式化验证、完整状态转移矩阵（那是技术评审的事）

> **得分异常？** 当本维度得分率 < 40% 时，查阅 `references/diagnostic-guide.md` 逻辑一致性章节定位根因。

### 信号质量扫描（逐维度交叉验证）

> 在每个维度审查结束时执行。七个维度检查"缺什么"，信号质量扫描检查"说了但没用"和"说了但是假的"。
>
> **完整指南：** 详见 `references/signal-quality-guide.md`（两类问题定义与示例、五条检测规则、降级规则、报告呈现模板）

**核心机制：** 信号质量不独立打分，作为各维度的**降级因子**：
- 发现废话/假话时，在对应维度的报告中标注 `[信号]` 并给出追问建议
- 某维度 > 30% 关键声明是废话/假话 → 该维度得分**封顶 60%**
- 某维度 > 50% 关键声明是废话/假话 → 该维度直接**降至 0 分**

**"关键声明"界定：** 目标/指标、功能核心动作、验收标准、非功能性需求的性能数字、数据模型中的约束规则。

---

### Step 2.5: 维度得分确认（检查点）

在进入汇总评分前，**暂停并展示各维度初步得分**，等待用户确认：

```
## 初步评审结果（待确认）

| 维度 | 初步得分 | 满分 | 得分率 | 主要发现 |
|------|:----:|:----:|:----:|---------|
| 完整性 | XX | 18 | XX% | 关键发现摘要 |
| 清晰度 | XX | 18 | XX% | ... |
| 可行性 | XX | 13 | XX% | ... |
| 风险识别 | XX | 13 | XX% | ... |
| 可测试性 | XX | 13 | XX% | ... |
| UX 一致性 | XX | 13 | XX% | ... |
| 逻辑一致性 | XX | 12 | XX% | ... |
| **初步总分** | **XX** | **100** | **XX%** | |

**信号质量降级（如有）：**
- 维度 X：> 30% 关键声明为废话/假话 → 封顶 60%（实际得分从 X → Y）
- 维度 Y：> 50% 关键声明为废话/假话 → 降至 0 分
```

> **确认问题：** "以上维度得分是否合理？如需调整某维度评分，请说明理由。确认后进入最终汇总。"

**用户可能的回应：**
- "确认" / "OK" → 进入 Step 3 汇总评分
- "维度 X 得分太低/太高，因为..." → 调整该维度评分后重新确认
- "维度 X 的扣分项 Y 不成立，因为 PRD 在 Z 处已说明" → 撤销该扣分项，重新计算维度得分

> **跳过条件：** 如果用户明确表示"直接输出最终报告无需确认"或使用 `--quick` 标志，可跳过此检查点直接进入 Step 3。

---

### Step 3: 汇总评分

1. 7 个维度得分求和（满分 100，最低 0）
2. 应用信号质量扫描的降级规则（封顶或置零）
3. 不及格项标记：单个维度得分率 < 40% 视为该维度严重缺陷
4. 映射到 A-F 等级

| 得分率 | 等级 | 含义 | 行动 |
|--------|------|------|------|
| >= 90% | **A** | 优秀 — PRD 质量很高 | 可以进入技术评审 |
| >= 75% | **B** | 良好 — 少量待补充项 | 补充后进入技术评审 |
| >= 60% | **C** | 及格 — 关键项基本覆盖 | 补充缺失项后可进入技术评审 |
| >= 30% | **D** | 不及格 — 存在重大遗漏 | 退回补充，重新评审 |
| < 30% | **F** | 严重不足 — 几乎没有可用内容 | 需重新编写 |

**及格线 60 分的含义：** PRD 至少需要：背景/功能范围/用户故事齐全、无严重歧义、外部依赖和现有系统关系明确、隐私/合规风险标注、验收标准可量化、关键页面有原型。

## 核心检查清单

审查时对照此清单（详见 `references/review-checklist.md`）：

- [ ] **完整性** — 背景/功能范围/用户故事/异常流程/业务数据/非功能性需求 到位
- [ ] **清晰度** — 术语统一、新概念有定义、无歧义、复杂流程有图、有优先级、规则有示例
- [ ] **可行性** — 现有系统关系明确、外部依赖声明、技术难点标注、工期有依据
- [ ] **风险识别** — 隐私数据标注、依赖风险评估、回滚思路、合规要求
- [ ] **可测试性** — 验收标准可量化、异常状态验收标准、成功度量指标
- [ ] **UX 一致性** — 交互不冲突、UI 状态完整、有关键原型、无障碍标注
- [ ] **逻辑一致性** — 规则无直接矛盾、规则竞争有优先级、因果链闭合、数值约束自洽、状态机完备
- [ ] **信号质量** — 无正确的废话（可执行删除测试）、无正确的假话（数字有测量方法和基线）

## Common Issues 常见问题

> **完整诊断指南：** 详见 `references/diagnostic-guide.md`，包含各维度得分低的原因分析和解决方案速查表。

**高频问题速查：**

| 问题 | 一句话解决 |
|------|-----------|
| 完整性得分极低 | 补充背景、用户故事、异常分支 |
| 清晰度得分极低 | 统一术语表，量化所有指标 |
| 文档充满"正确的废话" | 逐句做删除测试，将废话替换为可证伪声明 |
| 文档出现"正确的假话" | 每个数字补充测量方法和统计口径 |
| 可行性得分为 0 | 补充系统关系说明和依赖清单 |
| 风险识别得分为 0 | 逐项标注隐私数据和合规要求 |
| 可测试性得分极低 | 将验收标准改为可量化指标 |
| UX 一致性得分极低 | 补充空态/错误态/加载态/边界态设计 |
| 逻辑一致性得分极低 | 四步法逐项检查：冲突矩阵→场景穷举→约束方程 |
