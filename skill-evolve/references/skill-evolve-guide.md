# Skill 进化参考指南

## 反馈质量标准

### 好反馈的特征

好反馈能直接生成可执行的改进建议：

**结构完整：**
```markdown
### 基本信息
- 日期: 2026-05-10
- 涉及维度: 清晰度
- 错误类型: 误判

### 上下文
- 输入: 音视频直播 PRD，提到推流/拉流/GOP/CDN
- 实际输出: 清晰度维度扣 4 分，原因"新概念 GOP/CDN 未定义"
- 期望输出: 不扣分，这些都是音视频团队通用术语

### 根因
- 检查规则"新概念/领域术语有定义"未区分通用术语 vs 项目特有概念
- review-checklist.md 维度 2 的检查项缺少适用范围说明

### 建议
- 修改 review-checklist.md：术语检查增加"通用行业术语不扣分"说明
- 或将示例补充到 diagnostic-guide.md
```

**好的反馈**：明确指出哪里错了、为什么错、怎么改。每条结论可被代码验证。

**差的反馈**：笼统抱怨（"评分太低"）、无法复现（无具体案例）、无改进方向。

### 反馈信号识别

不是所有对话都值得记录为正式反馈：

| 信号 | 值得记录？| 理由 |
|------|----------|------|
| "这个扣分不对，因为 X" | ✅ | 有具体理由 |
| "评分太低了" | ❌ | 无具体理由 |
| "这里不应该扣分，PRD 在 XX 处已经写了" | ✅ | 有证据 |
| "这个流程不太对" | ⚠️ | 追问具体哪里不对 |
| 用户直接修改了 skill 文件 | ✅ | 事后应记录为反馈 |

## 6 种改进分类

### 1. terminology-calibration（术语/概念校准）

**定义：** 某个检查项的适用范围需要细化——对特定类型的内容不该扣分却扣了。

**识别信号：**
- 用户指出"这个不应该扣分，因为它是行业通用术语"
- 评分与人工判断偏差主要来自某一类概念的判断

**示例（prd-review 已有）：**
- 清晰度维度"新概念/领域术语有定义"：推流/GOP/CDN 等通用行业术语被扣分
- 修复：review-checklist.md 增加"通用行业术语（目标团队理应知道的）不扣分，仅项目特有概念扣分"

### 2. threshold-adjustment（阈值/边界调整）

**定义：** 扣分值、权重、得分率门槛等数值参数不合理。

**识别信号：**
- 某个维度反复得分集中在极低或极高区间
- 用户反馈"这个扣 5 分太重了"

**常见调整对象：**
- 维度权重
- 单项最高扣分
- 信号质量降级阈值（30%/50%）
- 及格线（60 分）
- 得分率 < 40% 的诊断触发条件

### 3. checklist-update（检查清单增删）

**定义：** 检查清单遗漏了该检查的内容，或包含了不该检查的内容。

**识别信号：**
- 审查报告漏掉了某类重要问题
- 检查项冗余或与其他维度重复

### 4. trigger-refinement（触发条件细化）

**定义：** Skill 该触发却没触发，或不该触发却误触发了。

**识别信号：**
- "我之前问了 X，但 prd-review 没有激活"
- "我只是在讨论 Y，prd-review 不应该跳出来"

**修复位置：** SKILL.md frontmatter 的 `description` 字段，或 When to Use 章节。

### 5. diagnostic-enhancement（边界/诊断规则增强）

**定义：** 边界场景处理不完善，或诊断指南对某些低分场景没有覆盖。

**识别信号：**
- 维度得分 < 40% 但 diagnostic-guide.md 没有对应的根因建议
- SKILL.md Step 1 的边界表中缺少常见场景

### 6. example-addition（示例补充）

**定义：** 缺少具体示例导致 AI 在不同场景下判断不一致。

**识别信号：**
- 同类型 PRD 两次评审结果差异大
- 用户反馈"这个判断标准太模糊"

## 严重程度定义

| 级别 | 定义 | 示例 |
|------|------|------|
| **高** | 会导致评分严重失真（偏差 > 20 分或 2 个等级）或系统性误判 | 维度检查清单遗漏核心检查项 |
| **中** | 影响一致性和准确性，但不会导致评分完全不可用 | 某项检查的适用范围需要细化 |
| **低** | 措辞优化、示例补充等可选项 | 某段描述可以更清晰 |

## Diff 呈现规范

### 格式

严格使用以下格式呈现变更建议：

```
### 建议 #N: [简短标题]

- **问题类型:** [类型]
- **关联反馈:** [文件名]
- **严重程度:** [高/中/低]
- **目标文件:** `[相对路径]`
- **目标位置:** [章节名 / 行号范围]

**变更内容:**
--- 原内容
[需要删除的原文]
+++ 新内容
[需要替换为的新内容]

**理由:** [1 句话说明为什么]
```

### 规则

1. `---` 块中的内容必须与当前文件精确匹配（先 Read 确认，再写 diff）
2. 每次建议只涉及一个文件的一个位置
3. 如果同一文件多个位置需要改，拆成多个建议
4. 变更理由必须引用具体的反馈证据

## 进化记录格式

每次应用变更后，创建 `skill-evolve/evolution-log/<skill-name>/YYYY-MM-DD-<slug>.md`：

```markdown
# 进化记录: [简短描述]

- **日期:** YYYY-MM-DD HH:MM
- **触发反馈:** [来源文件或会话 ID]
- **问题类型:** [6 类之一]
- **变更描述:** [1 句话]
- **影响文件:** [路径列表]
- **评估门控:** 🟢 passed / 🟡 warning / 🔴 blocked（含覆盖说明）/ ⚠️ 无 eval 用例
- **状态:** ✅ 已应用 / ❌ 已拒绝

## 变更详情

[具体的 diff]

## 用户决策
- 决策: [是/否/修改]
- 附加说明: [如有]
```

## 评估门控（Eval Gating）指南

> 受 Hermes Agent 约束门控机制启发——变更应用前用 eval 用例验证不会退化。

### 门控级别

| 级别 | 条件 | 行为 |
|------|------|------|
| 🟢 **passed** | 全部受影响用例预期不变或提升 | 正常进入审批 |
| 🟡 **warning** | 有用例预期下降，但核心用例不受影响 | 进入审批，标注风险 |
| 🔴 **blocked** | 核心用例（eval-001/002）预期下降 | 阻止自动审批，要求用户显式覆盖 |
| ⚠️ **no-eval** | 目标 skill 无 eval 用例 | 跳过，标注提醒 |

### 影响方向推断规则

基于改进建议的类型推断对 eval 用例的影响：

| 改进类型 | 典型影响 |
|---------|---------|
| terminology-calibration | 清晰度维度 ↑（减少误扣分） |
| threshold-adjustment（降扣分） | 各维度轻微 ↑ |
| threshold-adjustment（升扣分） | 各维度轻微 ↓ |
| checklist-update（新增检查项） | 对应维度 ↓（更严格） |
| checklist-update（删除冗余检查项） | 对应维度 ↑（更宽松） |
| trigger-refinement | 综合影响，需逐例分析 |
| diagnostic-enhancement | 边界用例 ↑（更好的异常处理） |
| example-addition | 各维度 →（一致性提升，分数不变） |

### 核心用例定义

对于审查/评分类 skill，以下用例被视为核心（退化会严重影响质量）：

- **eval-001**: 标准完整输入（验证基本评审能力）
- **eval-002**: 极简/劣质输入（验证缺陷检测能力）

这两个用例覆盖了"正常"和"异常"两端，任何改进不应同时降低两者的质量。

### 用户覆盖 🔴 blocked 的后果

当用户显式覆盖 blocked 后：
1. 变更正常应用
2. evolution-log 记录本次覆盖（含用户理由）
3. 下一次进化时，此 eval 用例的基线预期可能需要重新校准
4. 如果后续反馈证实了退化，应回滚并重新评估

## 自动触发机制

### 触发阈值

| 条件 | 行为 |
|------|------|
| 同一 skill 反馈 >= 3 条（未处理） | 会话结束前或下次对话开始时主动提示 |
| 同一 skill 反馈 >= 5 条（未处理） | 下次对话开始时强制提示（不可跳过） |
| 用户刚纠正了 skill 输出并被记录为 feedback | 当前会话结束前提示 |
| 用户直接修改了 skill 文件但未记录 feedback | 检测到 SKILL.md 变更后提示补充 feedback |

### 反馈"已处理"的定义

以下情况标记反馈为已处理：
- 反馈已被 skill-evolve 读取并生成了改进建议（无论用户是否批准）
- 用户在进化流程中明确回复"拒绝"或"否"
- 用户手动在 MEMORY.md 中移除了该反馈条目

### 提示模板

```
ℹ️ 检测到 prd-review 有 3 条未处理的反馈：
  1. 术语检查校准 (2026-05-10)
  2. ...
  3. ...

是否运行 "skill 进化" 分析这些反馈？
- "是" → 启动 skill-evolve 流程
- "稍后" → 暂时跳过，下次对话开始再提示
- "忽略" → 标记为已处理，不再提示
```

## 快速开始：新 Skill 接入

### 文件结构

```
<skill-name>/
├── references/
│   └── feedback-template.md    # 可选：skill 专用的反馈模板（有针对性的字段）
└── eval/
    ├── save-config.json         # L2+ 创建：skill-evolve 写入，告知 skill 持久化评审报告
    ├── results/                  # L2+ 创建：评审报告存档目录
    ├── eval-cases.json          # 可选：评估用例（用于回归检测）
    └── baseline.json            # 可选：基线分数
```

### 三级接入

| 级别 | 需要的文件 | 获得的能力 |
|------|-----------|-----------|
| **L1 基础** | 无（zero-config） | 反馈收集 + 模式分析 + 改进建议 + 人工审批（评审报告不持久化） |
| **L2 结构化反馈** | `references/feedback-template.md` + `eval/save-config.json` + `eval/results/` | 上述 + 反馈自动结构化解析 + 评审报告持久化 + 报告反馈匹配 |
| **L3 完整进化** | L2 + `eval/eval-cases.json` + `eval/baseline.json` | 上述 + 评估门控（变更前自动检测退化风险） |

### 接入步骤

**Step 1（L1 — 零配置）：** skill-evolve 自动发现 auto-memory 匹配的 feedback。
```
skill 进化 <skill-name>
```

**Step 2（L2 — 添加反馈模板 + 报告持久化）：** 复制通用模板并定制，创建持久化配置。
```
cp skill-evolve/references/feedback-template.md <skill-name>/references/
# 编辑模板，将"涉及维度"改为 skill 特有的评估维度

mkdir -p <skill-name>/eval/results
echo '{"output": "eval/results/"}' > <skill-name>/eval/save-config.json
```

**Step 3（L3 — 添加 eval 用例）：** 参考 prd-review 格式创建。
```
mkdir -p <skill-name>/eval
cp prd-review/eval/baseline.json <skill-name>/eval/
# 编辑 eval-cases.json，描述每个用例的输入和预期行为
```

> **1 个 eval 用例即可见效**：即使只有 1 个用例覆盖核心场景，评估门控就能标记退化风险。

## 进化常见问题汇总（完整版）

| 问题 | 处理方式 |
|------|---------|
| 反馈数量太少（< 2 条）| 降低置信度，只生成低风险的措辞/示例改进 |
| 反馈没有明确指出 SKILL.md 的问题 | 先反推可能的关联章节，标注 `[推测]` |
| 改进建议涉及多个文件 | 按依赖顺序排列，先改 SKILL.md 再改 references |
| 同一 skill 有多个版本的 feedback | 优先使用最新的反馈（按日期比较）|
| 某个改进建议用户反复拒绝 | 记录到进化日志 state=rejected，后续不再自动建议 |
| eval 用例过时或覆盖不全 | 标注 `⚠️ eval 覆盖不完整`，降低门控拦截力度 |
| 用户覆盖 🔴 blocked 后出现退化 | 在 evolution-log 记录退化情况，下次进化时优先关注 |

## 回滚常见问题汇总（完整版）

| 问题 | 处理方式 |
|------|---------|
| 回滚点无备份快照 | 提示手动操作：参考进化记录中的变更详情反向修改 |
| 回滚后还想恢复 | 备份不删除，可对新回滚记录再次回滚 |
| 回滚前文件已被手动修改 | 提示当前文件与备份 diff 有额外差异，让用户确认 |
| 用户选择回滚多个版本 | 按时间倒序逐个回滚，每步确认 |
| 回滚后发现原进化其实更好 | 对回滚记录再执行回滚即可恢复 |
