# prd-review 需求评审技能设计

## 概述

创建一个 Claude Code 技能，对产品需求文档（PRD）进行综合评审。输入为 PRD Markdown 文件 + 原型图/截图，输出 0-100 分量化评分和 A-F 等级，及格线 60 分。

## 目标用户

技术负责人/架构师为主，产品经理也可用于提交 PRD 前自检。

## 评分体系

### 等级映射

| 得分率 | 等级 | 含义 | 行动 |
|--------|------|------|------|
| >= 90% | A | 优秀 | 可进入技术评审 |
| >= 75% | B | 良好，少量待补充 | 补充后进入技术评审 |
| >= 60% | C | 及格，关键项基本覆盖 | 补充缺失项后可进入评审 |
| >= 30% | D | 不及格，存在重大遗漏 | 退回补充，重新评审 |
| < 30% | F | 严重不足 | 需重新编写 |

### 6 维度评分（满分 100）

每个维度有独立的满分、检查项、扣分规则和上限。同一问题不跨维度重复扣分。

---

## 维度 1：完整性（满分 20）

> PM 的核心职责——该有的内容是否都有。

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 缺少核心章节（背景/功能范围/用户故事） | -5/项 | -10 |
| 异常流程未覆盖（至少 3 条主要异常路径） | -3/条 | -9 |
| 业务数据需求缺失（字段清单/校验规则/权限矩阵） | -4/项 | -8 |
| 非功能性需求缺失（性能/兼容/安全等级） | -3/项 | -6 |

**PM 必须给出的信息（区别于技术评审的内容）：**
- 背景与目标：业务背景和要解决的问题
- 目标用户/角色：所有涉及角色（含管理员、外部系统）
- 功能范围 + 明确排除项："不做"的边界
- 用户故事 + 验收条件
- 业务流程：正常流程 + 至少主要异常分支
- 业务数据需求：需要记录什么信息、业务校验规则、谁可以访问
- 非功能性需求：用户感知的性能期望、安全等级要求、兼容范围

**PM 不必给出（属于后续技术评审）：**
- 数据库表结构、索引设计、存储方案
- API 接口定义
- 技术实现细节

---

## 维度 2：清晰度（满分 20）

> PM 的表达能力——写出来的东西是否无歧义、能直接执行。

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 术语不统一（同一概念多个名称） | -3/处 | -6 |
| 关键描述有歧义（可读出两种含义） | -4/处 | -8 |
| 复杂流程无图示（3 步以上交互） | -3/处 | -6 |
| 功能优先级未标注 | -4/次 | -4 |
| 规则缺少具体值或示例 | -2/处 | -6 |

**要求：**
- 术语统一：同一概念全文使用一致名称
- 无歧义表述："尽可能快"、"大概 100 条" 必须消除
- 复杂流程有图：3 步以上交互需要流程图/时序图
- 优先级标注：Must/Should/Could 分级
- 关键规则有示例："订单金额>=200 免运费"，而非"满足条件免运费"

---

## 维度 3：可行性（满分 15）

> PM 的工程意识——是否考虑了现实约束。

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 未说明与现有系统的关系（复用/改造/新增） | -5/次 | -5 |
| 外部依赖未声明（第三方服务/其他团队交付物） | -4/项 | -8 |
| 已有明确技术难点却未标注 | -3/处 | -6 |
| 工期评估无任何依据 | -3/次 | -3 |

**PM 必须给出：**
- 与现有系统的关系说明（哪些复用、哪些改造、哪些新增）
- 外部依赖声明（第三方服务、其他团队交付物、平台能力）
- 已识别的技术难点（PM 视角：这个需求团队以前没做过类似）

**PM 不必给出：**
- 技术方案选型、架构设计
- 性能基准测试预估
- 代码层面可行性分析

---

## 维度 4：风险识别（满分 15）

> PM 的风险嗅觉——业务的雷区是否标注。

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 涉及用户隐私数据却未标注 | -5/次 | -5 |
| 依赖风险未评估（外部服务/其他团队） | -4/项 | -8 |
| 无回滚/降级思路 | -3/次 | -3 |
| 合规要求未提及（金融/医疗/未成年人等） | -5/次 | -5 |

**PM 必须给出：**
- 业务风险：用户不接受、操作门槛高、数据准确性问题
- 合规风险：是否涉及用户隐私数据、是否需要法务审查
- 依赖风险：依赖方 SLA、是否有备选方案
- 回滚/降级思考：上线出问题影响多大、能否快速回退

**PM 不必给出：**
- 安全漏洞分析（技术评审）
- 技术架构风险（技术评审）

---

## 维度 5：可测试性（满分 15）

> PM 的验收能力——需求是否可被验证。

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 验收标准不可量化 | -4/处 | -8 |
| 异常状态验收标准缺失 | -3/处 | -6 |
| 缺少成功度量指标 | -3/次 | -3 |

**要求：**
- 验收标准可量化："用户 3 步内完成下单" 而非 "用户体验好"
- 核心路径验收场景：可验证的使用场景
- 异常状态验收标准：错误提示文案、重试行为、超时处理预期
- 数据指标/成功度量：上线后看什么指标判断功能成功

**PM 不必给出：**
- 测试用例、测试策略、QA 计划

---

## 维度 6：UX 一致性（满分 15）

> PM 的设计感知——交互是否与现有产品一致、UI 状态是否完整。

| 检查项 | 扣分 | 上限 |
|--------|------|------|
| 交互模式与现有产品冲突 | -4/处 | -8 |
| UI 状态覆盖不全（空态/错误态/边界态缺失） | -3/处 | -6 |
| 关键页面无原型/线框图 | -3/页面 | -6 |
| 需要无障碍却未提及 | -3/次 | -3 |

**要求：**
- 交互模式沿用现有产品习惯，不让用户学两套操作逻辑
- 所有 UI 状态覆盖：加载态/空态/错误态/边界态
- 关键页面有原型图/线框图
- 无障碍/国际化是否需要

**PM 不必给出：**
- 像素级视觉稿（设计师的事）
- 前端组件实现方案

---

## 审查流程

### Step 1: 输入接收与预处理

确认审查对象：
- Markdown PRD 文件：直接读取，识别章节结构
- 原型图/截图：查看图片内容，提取 UI 状态、交互路径信息
- 混合输入：PRD 文本为主，原型图为补充验证

输出：识别的输入类型 / PRD 大致结构 / 是否缺少关键输入

> **边界情况：** 仅提供原型图无 PRD 文本时，完整性/清晰度/可行性维度只能基于视觉内容做有限评估，需在报告中标注"因缺少 PRD 文档，以下维度无法完整评审"。

### Step 2: 逐维度审查

按完整性 → 清晰度 → 可行性 → 风险识别 → 可测试性 → UX 一致性顺序逐一审查：

1. 列出该维度检查清单
2. 逐条对照 PRD，记录证据
3. 发现缺失/缺陷时给出 `[事实]` 标注（引用原文行号或截图位置）和扣分
4. 无法从 PRD 确认的标注 `[推测]`，不扣分但记录

扣分约束：
- 每个维度扣分不超过其满分
- 同一问题不跨维度重复扣分

### Step 3: 汇总评分

- 6 维度得分求和（满分 100，最低 0）
- 不及格项标记：单个维度得分率 < 40% 视为该维度严重缺陷
- 映射到 A-F 等级

### Step 4: 生成评审报告

报告结构：
1. 总分概览：总得分/等级/各维度得分柱状示意/是否及格
2. 逐维度明细：得分/详细检查结果/问题列表
3. Top 问题排行：按严重性排序前 5 个问题
4. 改进路径：按 ROI 排序的补充建议，标注技术评审前必须补齐的项

## 技能文件结构

```
prd-review/
├── SKILL.md              # 技能入口
└── references/
    └── review-checklist.md   # 6 维度检查清单速查表
```

无 scripts 目录（PRD 评审核心是定性分析，AI 直接阅读和分析，不需要 shell 脚本做机械检查）。
